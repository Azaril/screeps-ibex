# Recon: existing simulation infrastructure vs. a new offline ECONOMY simulator

## 1. What `screeps-sim-core` models today, and its extension mechanism

**Scope: movement mechanics ONLY.** The kernel (`C:\code\screeps-ibex\screeps-sim-core`) is a JS-free port of the Screeps engine's movement half, extracted from the combat engine under ADR 0033 (`docs/design/0033-rover-pathing-sim-and-benchmark.md`). It models:

- **Terrain** — `SimTerrain { walls, swamps, roads }` as `HashSet<(u8,u8)>`; fatigue rates road=1/plain=2/swamp=10 with road-wins-over-swamp engine ordering (`screeps-sim-core/src/terrain.rs:9-38`, `constants.rs:12-21`).
- **Creeps + bodies** — `SimCreep { id, owner, pos, body, fatigue, carry_used }` (`world.rs:19-29`); `SimBody` = ordered part list, per-part 100-hit pools derived from a single `hits` total, boost tiers T1–T3 including CARRY capacity multipliers (`body.rs`). `carry_used` (total resources aboard) drives loaded-CARRY move-fatigue weight (`world.rs:39-41`) — so hauler load physics already exist.
- **Movement + fatigue + contention** — a faithful port of engine `movement.js check`: eligibility (MOVE part + fatigue==0), same-tile contention (rate1 swap/affected → rate2 pulled → rate3 pulling → rate4 move/weight), pull pairs, obstacle + recursive chain-block, edge-exit relocation as a separate phase (`movement.rs:98-281`, `tick.rs:25-83`). Multi-room via per-room terrain overrides `MovementState.rooms` (`world.rs:47-76`).
- **NOT modeled**: combat (lives in `screeps-combat-engine` as an overlay), spawning, energy, harvest, transfer, construction, controllers, labs, minerals.

**Extension mechanism** — exactly the layering contract an economy sim needs, and it is explicitly advertised for economy: the `Simulation` trait binds `(World, Intents, Report)` with a `step`; a new layer owns a world **containing** a `MovementState`, an intents type **embedding** `MoveIntents`, and calls `resolve_movement` at the movement point of its own tick pipeline — "No change to this crate is needed to add a layer" (`sim.rs:11-26`); the crate doc names "any future layer (economy, lifecycle)" (`lib.rs:6-9`). The combat layer is the worked example: `CombatWorld { movement: MovementState, towers, structures, controllers, safe_mode_owner }` (`screeps-combat-engine/src/state.rs:92-105`), combat `Intents` embed `MoveIntents`, and `resolve_tick` interleaves combat accumulate → shared movement → netting.

**Tick-stepped**: yes — one `resolve_movement` call = one tick, `world.tick += 1` (`tick.rs:78`); higher layers drive their own loops (haul fleet loop `screeps-rover-eval/src/haul.rs:376-457`; combat `resolve_tick`).

**Bit-determinism**: yes, by construction and fenced. The kernel deliberately avoids result-affecting `std HashMap` iteration (the OR-fold `tile_has_stayer` occupancy map with the loud comment on why a `HashMap<Position, CreepId>` collect would be an iteration-order determinism break, `movement.rs:226-241`, plus the permutation test `stacked_tile_obstacle_is_order_independent` `movement.rs:605-626`). Shared seeded RNG is SplitMix64 with zero ambient entropy (`rng.rs:1-40`). The fence itself is `sim_is_deterministic_over_rounds` in `screeps-combat-eval/src/tournament.rs:1163-1198` (5 rounds must have spread 0; two past leaks were in the rover resolver, both fixed). The bootstrap CI is also seeded ⇒ byte-reproducible reports (`screeps-rover-eval/src/stats.rs:6-9`).

**Rover driver** — `screeps-sim-core/src/rover_driver.rs` (feature `rover`) runs the REAL rover `MovementSystem` (resolver + `LocalPathfinder`) headlessly over a `MovementState`: `SimMoveRequest { goal, priority, priority_value (w-bid lane), shove, anchor, stuck_thresholds }` → `HashMap<CreepId, Direction>` per tick, with `MoverConfig` tunables (`rover_driver.rs:33-140`) and a persistent `SimMoveCache`. An economy sim gets live-parity creep movement for free through this.

## 2. Economy mechanics: modeled vs missing

**Already modeled (somewhere in the stack):**
- **Movement/fatigue/loaded-CARRY** — sim-core (above). Roads as fatigue-1 tiles; blocking structures as walls (`base_traffic.rs:68-87`).
- **Spawn-lane arithmetic (abstract)** — `screeps_combat_decision::spawn_throughput::spawn_step` is a pure, deterministic mirror of the live spawnsystem's per-room loop: descending priority, skip-if-over-capacity, **head-of-line break** if the top request isn't yet affordable, debit energy, `completes_in = part_count * CREEP_SPAWN_TIME(3)` (`screeps-combat-decision/src/spawn_throughput.rs:43-77`). The combat-eval lifecycle harness layers a colony model on it: homes with `energy_capacity` / `income`/tick (a **constant**, capped at capacity), spawn busy for `part_count*3` ticks, member TTL/renew churn (`screeps-combat-eval/src/harness/lifecycle.rs:6-11, 26-60, 89-127`). Note: this is a *mirror*, not shared code — the live bot's `spawnsystem.rs` does not call it (grep: zero references in `screeps-ibex/src`).
- **Actual spawn energy semantics (documented, not simulated)**: energy is withdrawn **atomically at `spawnCreep`** (fails atomically if available < cost), drawn spawns-first then extensions-closest-first unless `energyStructures` given (`docs/references/engine-mechanics.md:257`); duration `3 × body.length` ticks, one creep per spawn, blocked-exit slip (`engine-mechanics.md:242, 288-292`). There is **no** 1-energy/tick drain during spawning — the prompt's "drain" framing is wrong and the doc has the correct mechanics.
- **Controller de-claim only** — `SimController { owner, downgrade_ticks }` for `attackController` (`screeps-combat-engine/src/state.rs:71-83`); explicitly "the full upgrade-block / reservation mechanics are not modeled".
- **All the constants + formulas, verified against the cloned engine** — `docs/references/engine-mechanics.md` §7.4 table (line-checked against `common/constants.js`): HARVEST_POWER 2/WORK/tick; source capacity 3000 owned/reserved, 1500 neutral, 4000 SK, 300-tick regen with the timer starting at first harvest below cap (`engine-mechanics.md:445`); UPGRADE_CONTROLLER_POWER 1 e/WORK/tick with the RCL8 15/tick cap; CONTROLLER_LEVELS {1:200 … 7:10.935M} and DOWNGRADE {1:20K … 8:200K}; EXTENSION_ENERGY_CAPACITY 50 (RCL≤6)/100 (RCL7)/200 (RCL8) → 12,900 room max; LAB reaction 5/boost 30 mineral + 20 energy; minerals 50k-tick regen with density tiers (`engine-mechanics.md:446, 449-467`). Build: `BUILD_POWER` = 5 progress per WORK per tick at 1 energy per progress point — i.e. 5 energy/WORK/tick while building (transcribed as `BUILD_POWER_E_T = 5.0` and `UPGRADE_POWER_E_T = 1.0` in `screeps-rover-eval/src/value.rs:48-51`). Rate-level economy math also exists in the pure `room_economics.rs` ROI kernel (`screeps-ibex/src/room_economics.rs:34-58`: source capacities, HARVEST_POWER, body costs, CREEP_LIFE_TIME amortization).

**Missing (must be built for the economy sim):** actual tick-resolved **harvest** (2/WORK/tick decrementing a source with the 300-tick regen state machine), **store/transfer/withdraw/pickup** (the sim's `carry_used` is a single summed number, instant-load in the haul bench `haul.rs:358, 434-441`), **controller upgrade + RCL progression + downgrade timers**, **construction sites/build progress**, **extensions as energy stores refillable per RCL**, **spawn objects that create sim creeps** (combat's `SimStructure::Spawn` is only a damage target), **labs/minerals/extractor mechanics** (zero lab mechanics anywhere in the sim stack), **energy income as an emergent quantity** (lifecycle harness uses a constant income scalar). None of these are hard: the layering contract in `sim.rs` is designed for exactly this overlay, and every needed formula is already transcribed with engine-source citations.

## 3. Scenario definition + metrics reporting in rover-eval — what an economy bench reuses verbatim

- **`stats.rs` — reuse 100% verbatim.** Pure math over `(value, weight)` samples: `weighted_mean`, `percentile_sorted`, seeded `bootstrap_weighted_mean_ci` (2000 resamples, 95%), and `Summary { n, weighted_mean, ci95, min, p05..p95, max }` (`screeps-rover-eval/src/stats.rs:33-115`). A "bootstrap recovery time" or "time-to-RCL-N" metric drops straight in as samples.
- **Scenario shapes.** Tier-A single-creep: `Scenario { name, terrain, spec, from, goal, range, max_r_fatigue, max_r_ticks }` + `validate()` producing pass/fail + per-gate failure strings, with a curated `catalog()` and a seeded procedural `generate(seed)` (`scenario.rs:37-199`). Fleet-level: `HaulAssignment { body, q, source, sink, trips }` + `HaulOutcome { samples, summary, audit, completed_trips, expected_trips, ticks, deadlocked }` (`haul.rs:87-110`); corpus-level: `TuneScenario { name, family, terrain, rooms, fleet, tick_cap }` with per-family H reporting + pooled H, and the deterministic gates-first `ranked_key()` (quantized milli-H, no raw-float compares) (`tuning.rs:63-116`). The economy analogue would be `EconScenario { layout/terrain, rcl, sources, start-state, tick_cap }` → samples like `(T*_recover / T_recover, weight)`.
- **Metrics idiom.** Ratio-vs-oracle metrics: `R_fatigue`, `R_ticks`, `movement_eff`, `fatigue_util` (`metrics.rs:1-120`); the haul objective `H = Σ Wη / ΣW` with η = T*_rtt/T_rtt against a fatigue-exact oracle and W = cargo (`haul.rs:1-12, 305-326`). "Bootstrap recovery time" fits this exactly: realized ticks vs an analytic optimum (e.g. energy-throughput-bound lower bound on time-to-RCL-N), 0-scored on non-completion so the catastrophic tail stays visible (`haul.rs:305-315`).
- **Hard-gate sentinel.** `IntentAudit` reconciles issued directions vs engine-executed moves each tick and classifies failures (fatigued/wall/parked/coordination), with `failed_coordination == 0` gated everywhere (`crowd.rs:64-102`); deadlock detector = 12 consecutive zero-movement ticks (`haul.rs:31-32`). Reuse as-is for economy fleets.
- **CLI shape.** `rover_bench` bin: `cargo run --release -p screeps-rover-eval --bin rover_bench -- fast|full`, env-var overrides (`BENCH_SEED`, `BENCH_REUSE`, …), per-scenario lines + per-family H + pooled H + audit totals, non-zero exit on gate failure (`src/bin/rover_bench.rs:8-118`). The tournament/sweep is an env-driven `#[ignore]` test doing coordinate descent over config layers (`tuning.rs:1-41`). Both patterns transplant directly (`econ_bench` + an `#[ignore]` policy sweep).
- **Tick-loop template.** `simulate_fleet` (`haul.rs:336-457`) is the exact skeleton an economy sim extends: per-tick build `SimMoveRequest`s → `resolve_moves_via_system_with` → `resolve_movement` → audit reconcile → domain state transitions (leg/arrival logic — where harvest/transfer/build/upgrade resolution would slot in).

## 4. Can the REAL bot decision code run against a sim world?

**Combat: yes, via an extracted JS-free decision crate + DTO seam — this is the proven pattern.** The tactics live in `screeps-combat-decision` (a separate crate, no `game::*`): `CombatCreepDto`/`CombatStructureDto`/`SquadStateDto` value types, the read seam `CombatView` (`screeps-combat-decision/src/lib.rs:116-213`), the write seam `enum CombatIntent` (`lib.rs:230-239`), and pure kernels (`decide_combat` `lib.rs:459`, plus force_sizing, composition, rally, lifecycle, spawn_throughput, kite, assignment…). Two adapters exist: the **live** bot builds the DTOs from real `Creep` handles (`screeps-ibex/src/jobs/squad_combat.rs`; bot dep at `screeps-ibex/Cargo.toml:36`), and the **sim** adapter `screeps-combat-agent::SimView` builds them from a `CombatWorld`, minting synthetic `RawObjectId`s and translating intents back to engine actions (`screeps-combat-agent/src/lib.rs:1-100`). Self-play is therefore `IbexAgent` vs `IbexAgent` with "no fork to drift or overfit" (`lib.rs:5-8`).

**Economy: NO — the bot's economy logic is hard-coupled to the JS game API and the specs ECS.** The mission/job layer runs against live handles: `JobExecutionRuntimeData.owner: &'a Creep` (the wasm-bindgen game object; `screeps-ibex/src/jobs/jobsystem.rs:44-55`), jobs are `screeps-machine` state machines calling behaviors that read `creep.store()`, `creep.room()`, transfer tickets, the repair queue, ECS `Entity` room data (`jobs/harvest.rs` throughout — e.g. the opportunistic-repair calls embedded in the Harvest/Delivery states at `jobs/harvest.rs:225, 264` → `jobs/utility/repairbehavior.rs:111`, which is precisely the operator's low-EV-repair-under-stress complaint site). The spawn system reads `game::rooms()`, live `StructureSpawn`, `room.energy_available()` (`spawnsystem.rs:379-425`). The transfer system is ECS+`screeps::*`-bound with direct `game::rooms()` reads (`transfer/transfersystem.rs:132`).

**Consequence for the new sim:** out of the box, an economy sim can test **re-implementations/mirrors** (the `spawn_step` mirror pattern — faithful, citation-pinned, but a fork) or **pure kernels that already exist** (`room_economics.rs` net-ROI, `claim_economics.rs`, `spawn_throughput`). To test THE REAL bot economy logic the way combat does, the economy decision layer must first be extracted behind a DTO seam (an `EconomyView`/`EconomyIntent` analogue of `CombatView`/`CombatIntent`) — which is also exactly the operator's ask (a): a simpler, pure, testable energy-prioritization policy layer that both the live bot and the sim consume. Precedents inside the bot crate for such extraction: `room_economics.rs` ("functionally PURE kernel — NO game::* / world reads", `room_economics.rs:10-25`) and the spawn head-of-line model already reproducing the live 3/5-stall class offline (`spawn_throughput.rs:98-173` — the head-of-line break is itself an energy-prioritization-under-scarcity mechanism the operator's problem lives in).

## Bottom-line reuse map for the new economy sim

- **Reuse unchanged:** sim-core kernel (movement/fatigue/bodies/multi-room/`Simulation` layering), `rover_driver` (real rover movement), `stats.rs` (CI/percentiles), `IntentAudit` + deadlock sentinel, `rng.rs`, terrain decode + captured layouts + `base_scenario`, the `rover_bench`/tuning CLI + corpus/family/ranked-key idioms, engine-mechanics.md as the formula ground truth, `sim_is_deterministic_over_rounds` as the fence pattern.
- **Build new (an "economy overlay" crate mirroring `screeps-combat-engine`'s relationship to sim-core):** `EconWorld { movement: MovementState, sources, minerals, spawns, extensions, controller, sites, stores, labs }`, `EconIntents { moves: MoveIntents, harvest/transfer/withdraw/build/upgrade/spawn }`, `resolve_econ_tick` calling `resolve_movement` at its movement point — every formula already transcribed and cited.
- **Decision-layer choice to surface to the operator:** scripted/kernel-driven economy policy (fast; tests a policy, not the bot) vs. extracting an `EconomyView`/`EconomyIntent` seam from the jobs/missions layer (tests the REAL bot logic; this is what made combat's offline findings transfer live, and it directly serves ask (a) — a simple pure stress-priority kernel).
- **Metrics:** "bootstrap recovery time" and "time-to-RCL-N" as η-vs-analytic-optimum samples through `Summary`, with hard gates (no deadlock, audit==0) underneath — the exact H-metric architecture. The live-side complement already exists: ibex-eval's `colony_health` econ term (gcl+rcl-progress+stored-energy per tick, `screeps-ibex-eval/src/score.rs:73-96`) for Docker validation of what the offline sim predicts.
